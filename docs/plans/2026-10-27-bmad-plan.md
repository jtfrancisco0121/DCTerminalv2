# BMAD planning in Eagle-Eye

Status: approved 2026-10-27 (JT: pin ADE's `bda3c59` and reuse its runtime; Auto uses the sizing rules below). Build after P5 (the first real Koneksi run in GitHub review mode).

## Why

Our Planner writes one `plan.md` from its own prompt. For a Large ticket that is thin: no PRD, no architecture decisions, no UX, so gaps show up in review rounds instead of before the build. ADE (`~/Documents/Projects/better-agentic-ide`) gets that depth from BMAD v6, but it commits BMAD into every repo and only *asks* its roles to use it ("prefer these skills"). We take ADE's packaging and keep our delivery and enforcement:

| | ADE | This plan |
|---|---|---|
| Where BMAD lives | `.claude/skills`, `_bmad/`, `_bmad-output/` committed in the repo | Inside the dcv2 plugin; outputs in the run folder. Nothing in the repo or worktree. |
| Python / `uv` | Removed: vendor-time patch to a Node runtime | Same |
| Pinned | One upstream commit | Same |
| Is it used? | Role text says "prefer" | `state.sh` refuses plan approval without the documents when the run is in BMAD mode |
| Who decides "done" | ADE gates (written by QA, an agent) | Unchanged: our gates + the app's own check re-run. BMAD never builds, reviews or ships. |

## The flow (BMAD mode on)

```
Planner, sizing pass → Small | Medium | Large (+ reasons)          [Auto mode only]
Large (or mode = On):
  Planner, BMAD pass → run/bmad/output/: spec (kernel), architecture,
                       PRD (new user-facing feature), UX (UI changes)
  S bmad-check        → documents exist, non-empty, BMAD's own validate passes
Planner, plan pass    → plan.md (stories + PRs) built from those documents,
                        each story naming the spec/PRD items it covers
Plan Reviewer         → reviews plan.md AND the BMAD documents, incl. drift between them
⏸ Stop #1             → the app panel links each document
Build / PR review     → as today; PR Reviewer also checks drift against the documents
```

Small and Medium in Auto mode: exactly today's flow.

## What changes

| Area | Change |
|---|---|
| Vendoring | `plugin/bmad/` (not `plugin/skills/`, so the 30+ skills are not registered in every session and don't fill the context): `VERSION`, `LICENSE` (BMAD's MIT), the allowlisted skills, `runtime.mjs`. Script `scripts/vendor-bmad.sh <sha>`: clone, check out, copy, patch, run the patch tests. Manual, like ADE's. |
| Allowlist | `bmad-spec`, `bmad-prd`, `bmad-architecture`, `bmad-ux`, plus whatever they reference (the `bmad` core skill, `bmod-core-tools`). Left out: personas, `bmad-build(-auto)`, `bmad-code-review`, `bmad-qa-generate-e2e-tests`, `bmad-ticket`, party mode, retrospective. One definition of done, ours. A test fails when an allowlisted skill references a skill that was left out. |
| Patcher | `scripts/patch-bmad.ts`, run at vendor time, idempotent, **throws on anything it does not recognise**: (1) `uv run …/scripts/<x>.py` → `node {bmad-runtime} <x>`; (2) `{project-root}/_bmad/…` → `{bmad-root}/…` and `{project-root}/_bmad-output` → `{bmad-output}`; (3) the "`{project-root}` is the nearest folder containing `_bmad/`" convention line → `{project-root}` is the repo/worktree being planned, `{bmad-root}` = `<run>/bmad`, `{bmad-output}` = `<run>/bmad/output`, `{bmad-runtime}` = `${CLAUDE_PLUGIN_ROOT}/bmad/runtime.mjs`. Repo paths such as `{project-root}/docs/standards.md` stay read-only references to the repo. |
| Runtime | Node port of the Python scripts the allowlisted skills call (see decision 1). Writes only under `{bmad-root}`; refuses any other path. Tests prove it. |
| `state.sh` | `bmad-init <run>`: creates `<run>/bmad/` with `config.toml` (project name, output folder in the run) — no customisation folder. `bmad-check <run>`: the required documents for the run's size exist, are non-empty, and pass the skill's own validate step; prints one status line. `S put` refuses `stage: plan-approval` when `meta.json` says BMAD applies and `bmad-check` has not passed. |
| Planner | New `pass` input: `size` (returns `{"size": "...", "reasons": [...]}`, writes nothing) and `bmad` (reads the allowlisted `SKILL.md` files by path from `${CLAUDE_PLUGIN_ROOT}/bmad/skills/` and follows them in headless mode, with the ticket text, the repos and the codebase memory as input). The normal pass reads `<run>/bmad/output/` when it exists. Sub-agents have no Skill tool, so skills are read and followed as files; the B1 spike confirms headless mode works that way. |
| Sizing rules (Auto) | Large when any of: more than one repo; a new API, data model or migration; a new user-facing feature or screen; more than about five stories; the ticket is a feature/epic. The Plan Reviewer may say "this is Large" as a MEDIUM finding → the run goes back for the BMAD pass. |
| Guard | Planner may run `node ${CLAUDE_PLUGIN_ROOT}/bmad/runtime.mjs …` and write under `<run>/bmad/`; still no writes in repos or worktrees. No other role runs the runtime. |
| Plan Reviewer | Reviews the BMAD documents too: untestable requirements, unhandled failure modes, and drift (plan.md must cover the spec/PRD items it claims; architecture decisions are followed). |
| PR Reviewer | Drift check against the run's BMAD documents when they exist (ties in with the "try to break it" reviewer change, a separate small PR). |
| meta.json | `bmad`: `{"mode": "auto"|"on"|"off", "version": "<sha>", "size": "...", "applied": bool}`. A run with no `bmad` field = off, so old runs resume unchanged. |
| App | Start screen: "BMAD planning: Auto / On / Off", default Auto, remembered per repo. Run panel: size + reasons, links to each document at stop #1, "BMAD <version>" badge. |
| Tests | Patcher (every rewrite, idempotence, throws on an unknown call site, fixtures from the real pinned tree); runtime (each command, refuses paths outside `{bmad-root}`); `bmad-check` and the `S put` refusal; guard allow/deny; a golden run per mode (off, on) on haiku with a toy repo; an old-run resume with no `bmad` field. |

## Decisions (JT, 2026-10-27)

1. **What to pin.**
   - **(a) Chosen:** ADE's pin `bda3c59` ("6.13.0-next") and reuse ADE's `ade-runtime.mjs` (MIT, © Alvin Reyes; keep the notice). It already ports every script that tree calls and has tests. B1 shrinks to a few days.
   - (b) The 6.12.4 tag we picked on 2026-10-22 and port the Python ourselves. More work; ADE notes that the v6 tags "carry the old layout", so (a)'s runtime would not fit it.
2. **Auto threshold.** Chosen: the sizing rules above (not the stricter "only On when switched on").

## Things to know

- **Cost and time.** A Large run gains one Opus planning pass (spec, architecture, maybe PRD/UX) and a longer plan review. Small and Medium runs cost nothing extra in Auto. B4 measures it.
- **Work repos stay clean.** No BMAD file is written in a repo or worktree, so nothing shows up in a PR.
- **Names.** BMAD code is MIT, but "BMad" is a trademark: the UI says "BMAD-METHOD skills" as a compatibility statement, no logo.
- **v7.** BMAD v7 changes the install (plugins/marketplace). We stay pinned; moving to v7 is a deliberate re-vendor, likely simpler since it is closer to our plugin model.

## Spike result (2026-10-27, `scripts/skill-e2e/bmad_spike.sh`)

- **Headless worked.** Model: haiku (the script's default; 74 s). The Planner (`claude -p --agent dcv2:planner`, `pass=bmad`) read `plugin/bmad/skills/bmad-spec/SKILL.md` by path, wrote `bmad/output/r-spike/spec-tally-validation/spec-tally-validation.md` with an `id: SPEC-…` frontmatter and CAP items, and wrote `.memlog.md` through `node "<plugin>/bmad/runtime.mjs" memlog init|append`, with the run path `…/App Support/runs/r-spike` (a space) quoted in every call. The toy repo stayed clean and the guard blocked nothing.
- **What the role had to override or add.**
  - bmad-spec has no `references/headless.md` (its headless text is `assets/headless-schemas.md` plus the Workspace and Intent sections of SKILL.md); the role now says so, after the first Read failed.
  - The Planner added `DCV2_RUN_DIR="<run>"` to its runtime calls by itself; the role keeps that as the fix when the variable is missing.
  - The model skipped the skill's `resolve_config` / `resolve_customization` activation calls and used the defaults. The output folder (`<run>/bmad/output/<run id>/spec-<slug>/`) was still right, because the prompt and `bmad-init` fix it. The documents are checked by `state.sh bmad-check`, not by how the skill was walked.
  - Not exercised by the spike (golden `bmad` case): PRD/UX Validate, the architecture reviewer gate and `lint_spine`.
