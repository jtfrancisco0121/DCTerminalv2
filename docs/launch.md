# Launch contract (app ↔ plugin)

How the app (P3) starts a Claude session with the dcv2 plugin, and the files the plugin (P2b) provides for it. Both sides build against this page; change it first when the contract changes.

## Command

```
cd <start folder>
env CLAUDE_CONFIG_DIR=<account dir> \
    DCV2_RUN_DIR=<run dir>                # Eagle-Eye only
    DCV2_MEMORY_DIR=<app data>/memory     # always
    DCV2_MAX_IMPLEMENTERS=<n>             # Eagle-Eye only; default 3 (setting); the run's meta.json `maxImplementers` wins when present (start and resume)
    DCV2_STOP_HOOKS=on|off                # A3 kill switch; default on (setting)
    DCV2_SLOP_CHECK=on|off                # the Stop hook's slop check; default on (setting run.slopCheck)
    DCV2_TAB_ID=<tab id> DCV2_HOOK_PORT=<port> DCV2_HOOK_TOKEN=<per-launch token>   # A2 forwarder (P3)
  claude --plugin-dir <plugin> \
         --settings <launch settings file> \
         --append-system-prompt-file <memory prompt file> \
         [--model <m>] [--permission-mode <mode>] \
         "/dcv2:eagle-eye run=<run dir>"   |  "/dcv2:eagle-eye resume run=<run dir>"  |  "/dcv2:<role> <request>"
```

`<plugin>` is the plugin folder shipped in the app bundle (dev: `<repo>/plugin`).

`--model` and `--permission-mode` are added to **Eagle-Eye tabs only** (start, queue, wave, eval and resume: the launches with a run folder), by `run/launch.rs` `launch_spec`; role, plain and plain-resume tabs never get them. The model is the account's `orchestratorModel` override, else `run.orchestratorModel` (default `opus`); the mode is `run.orchestratorPermissionMode` (default `auto`; `auto`, `acceptEdits` or `default`, never `bypassPermissions`). An empty or invalid stored value adds no flag (the account's own model or mode applies). A save of an invalid changed value is refused and the old value kept. Both are recorded in the run's meta.json `orchestrator`; a resume uses the recorded pair when the run has one, else the current settings. They ride in the tab's launch record, so a reopened tab keeps them.

## Files the plugin provides (P2b)

| File | Use |
|---|---|
| `plugin/VERSION` | One line: the roles' version (A5). The app shows it and records it in each run's `status.json`-adjacent `meta.json` (P3). |
| `plugin/launch/settings.json` | A4 token savers: `env` (`BASH_MAX_OUTPUT_LENGTH`, `CLAUDE_CODE_SUBAGENT_MODEL` only if the agents don't name one, autocompact threshold), `permissions.deny` (`node_modules/**`, lockfiles, build output). The app merges its own hook-forwarder `hooks` into a copy (per launch, in the run folder or a temp dir) and passes that copy with `--settings`. Never written into repos or `~/.claude*`. |
| `plugin/scripts/memory.sh` | The only code that knows the memory layout (D9). Commands below. |
| `plugin/skills/onboard/SKILL.md` | `/dcv2:onboard` (a role tile). |

### memory.sh

All commands read `DCV2_MEMORY_DIR` (or `--root <dir>`), print nothing secret, exit non-zero with one stderr line on error.

| Command | Output |
|---|---|
| `memory.sh id <repo path>` | The repo id: from `origin`'s URL (`host__owner__name`, lowercased, `.git` dropped), else `local__<folder name>-<first 8 hex of sha1(abs path)>`. Stable across accounts and clones. |
| `memory.sh compose <start folder> <out file>` | Writes the system-prompt file for a launch: the trust rule, the memory root path, `workspace.md` (folder of repos) + contracts, each in-play repo's `index.md`, and a list of stale topics. Always succeeds when the folder exists; with no memory it writes a short "no memory yet, `/dcv2:onboard` creates it" note. Bounded size (caps below). |
| `memory.sh status <start folder>` | JSON for the app panel: `{"schema":1,"workspace":{"present":bool,"path":..}|null,"repos":[{"name","path","id","present","head","topics":[{"name","checkedAt","stale":bool}],"staleCount","indexBytes"}]}` |
| `memory.sh write <repo id or "workspace:<id>"> <relative file> < content` | The only write path for agents: enforces size caps, secret scan, pinned lines (`<!-- pinned -->` lines cannot be removed or changed by an automatic write), topic header. Rejects with a reason. |
| decision log: `topics/decisions.md` (repo or workspace) | A topic that holds only `- YYYY-MM-DD | decision | reason | rules out: what` bullets (plus the topic header): `memory.sh write` rejects any other line (`REJECTED: ...`), `compose` loads it right after the contracts under the heading "a plan that contradicts an entry must state why its reason no longer holds", and `learn` refuses it. Planner, Plan Reviewer, Risk Reviewer and Recommendation read it; the memory updater records a plan's approved `## Decisions`; the developer role records a decision the user makes. Seed for this repo: `fixtures/memory/dcterminalv2-decisions.md` (no hosted CI, no phone app, approvals only in chat, one PR per repo per run); write it once, by hand, with `sed "s/@SHA@/$(git -C <repo> rev-parse HEAD)/" fixtures/memory/dcterminalv2-decisions.md \| bash plugin/scripts/memory.sh write <repo id> topics/decisions.md`. |
| `memory.sh learn <repo id or "workspace:<id>"> <topic or index> < lines` | Adds each stdin line (the `Learned:` lines of a run) under the file's `## Gotchas`, one result line per input: `added`, `duplicate` (equal after normalising, or word-set Jaccard >= 0.8 with an existing line) or `refused <reason>` (a secret-like line, over 300 characters, over the size cap; the other lines are kept). `write` and `learn` hold a lock on `<memory root>/.lock` (`dcv2_portable.lock`: `flock` on POSIX, `msvcrt.locking` on Windows, retried for at most 25 s) around read-merge-write, so runs finishing together lose no line; when another `memory.sh` still holds it after 25 s, the command exits 1 with "memory lock busy: another memory.sh is still running (waited 25 s)" (shorter than the app's 30 s timeout, so the panel shows this line). The file must exist. |
| `memory.sh scan < text` | The secret scanner alone: `clean` (exit 0), or `looks like a secret on line <n> (<kind>)` (exit 1), never the value. `state.sh` runs it on every GitHub post (fails closed when it cannot run). |

### Git Bash (app-run scripts on Windows)

The app starts `memory.sh` (and every plugin script it runs) through `platform::script_command`. On macOS and Linux that is `bash` from PATH. On Windows it is an absolute Git Bash path, never a bare `bash` (CreateProcess searches `System32` first, where WSL's `bash.exe` lives). The one resolution order, used by the Rust resolver (`src-tauri/src/platform/mod.rs`) and the gate's JS port, and tested against `fixtures/platform/git-bash-cases.json`:

1. `CLAUDE_CODE_GIT_BASH_PATH`, when it is a file (the app keeps it in the env it gives Claude tabs, so the app and Claude agree);
2. `%ProgramFiles%\Git\bin\bash.exe`;
3. `%ProgramW6432%\Git\bin\bash.exe`;
4. `%ProgramFiles(x86)%\Git\bin\bash.exe`;
5. `%LOCALAPPDATA%\Programs\Git\bin\bash.exe`;
6. `git --exec-path`, three folders up, `bin\bash.exe`.

Any candidate under `%SystemRoot%\System32` or `WindowsApps` is rejected. With no match the Memory panel shows "Git Bash not found. Install Git for Windows or set CLAUDE_CODE_GIT_BASH_PATH.". Every non-PTY child is built by `platform::quiet_command` (no console window on Windows), and a child that may time out is started with `platform::spawn_group` and stopped with `platform::kill_tree`.

### Python (plugin scripts)

`guard.sh`, `memory.sh`, `state.sh` and `stop-check.sh` embed Python and start it only through `plugin/scripts/lib/python.sh` (sourced from the script's own folder; `guard.sh` uses its pure-bash folder because the PATH may be broken). The picker sets the array `DCV2_PY` to the first of `python3`, `python`, `py -3` for which `import sys; sys.exit(0 if sys.version_info >= (3, 8) else 1)` exits 0, and stops at the first that works; the Microsoft Store stub exits non-zero, so it is skipped. A script runs `"${DCV2_PY[@]}"` only after checking `${#DCV2_PY[@]} -gt 0` (bash 3.2 under `set -u` cannot expand an empty array). With no usable Python, `guard.sh` still fails closed and says "install Python 3.8+ (tried python3, python, py -3)", `memory.sh` and `state.sh` print one error line naming the same three commands, and `stop-check.sh` skips (no check), as before. The guard's interpreter rules also know the Windows spellings: `py` (and its `-3` flag), a `.exe` after any interpreter or shell name, and `bash.exe`.

### Shared plugin Python (`plugin/scripts/lib/dcv2_portable.py`)

Every OS difference of the plugin's embedded Python lives in this stdlib module: the bounded lock, `spawn_group`/`kill_group` (POSIX `start_new_session` + `os.killpg`; Windows `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP` + `taskkill /F /T`), the retrying `replace`, and the path functions in docs/run-folder.md. Each script puts its own `scripts/lib` first on `sys.path` from its own path (through `DCV2_LIB_DIR`, which the script sets itself on the Python command line, never read from the caller's environment), sets `sys.dont_write_bytecode = True` before importing it (no `__pycache__` in the sealed app bundle), and the plugin test fails if a `__pycache__` appears under `plugin/`.

`state.sh put <path> < json` is the one way the skill writes status.json: the path must be `$DCV2_RUN_DIR/status.json` (exact name, same real path); any other path, name or an unset `DCV2_RUN_DIR` is refused with nothing written.

The guard blocks Edit/Write into `DCV2_MEMORY_DIR` (agents use `memory.sh write`). The app's own memory editor (P3) writes files directly, as the user.

## Run folder additions (P2b)

- `meta.json` gains `"reviewMode": "github" | "local"` (app-written at Start from the start-screen toggle "Review on GitHub (draft PRs)"; guard-protected; missing = `local`). The plugin reads it only through `state.sh mode` / `preflight` and branches on it (run-folder.md, Review mode).
- `meta.json` gains `"bmad": {"mode": "auto" | "on" | "off", "version": "<plugin/bmad/VERSION line>"}` (app-written at Start from the start-screen control "BMAD planning (BMAD-METHOD skills)"; guard-protected; missing = `off`). `state.sh preflight` prints `bmad=auto|on|off` and `node=<version>|missing` (BMAD's runtime is Node 18+; auto/off runs never need it). The plugin reads the mode only through `state.sh` (run-folder.md, BMAD mode).
- `repos.json` repos gain `"setup": "<command>" | null` and `"copyFiles": ["relative/path", …]` (app-written; run-folder.md, repos.json): `state.sh worktree` copies the git-ignored files and runs the setup in newly made worktrees, output in `logs/<PR>-setup.txt`.
- status.json PRs gain `draft` (bool) and `comments` (`[{"round", "url"}]`) and the state `drafted` (github mode); `opened` means ready for review. Schema stays 1 (optional fields).
- `pr-comments/<PR>-round<n>.md`: what was posted (github mode).
- Guard (0.3.0): the orchestrator runs no GitHub-writing `gh` at all (`gh api` with a non-GET method or `-f/-F/--field/--raw-field/--input`, `gh <x> create|comment|edit|ready|…`); in github mode it pushes and posts only through `state.sh` (after the plan approval; `ready` after the ship approval); `security dump-keychain` and `security find-*-password … dcterminalv2…` are blocked for everyone in a run.
- `gates/<PR id>.yml` (A1): written by the PR Reviewer step through `state.sh gate`: `gate: PASS|CONCERNS|FAIL|WAIVED`, `reason: <one line>`, `updated: <UTC>`, `review: <review file>`. A PR is green in the app only when the gate is PASS or WAIVED **and** the app's own check re-run (R1) passes.
- `report.md` (R10): written at `done`/`failed`: planned vs built per PR, review rounds, retries, gate per PR, check results.
- `memory-update.md`: what the end-of-run memory update changed (or "no topic touched").
- **AFK runs (0.5.0, plan 2026-10-27).** `requests/<id>.json` (written by `state.sh request <run> recheck|cleanup|tickets|selftest`, `{"schema":1,"id","kind","at"}`, id `<YYYYMMDDTHHMMSSZ>[-n]-<kind>`) asks the app for one of its fixed actions; the app answers in `requests/<id>.result.json` (`{"schema":1,"id","kind","state":"running|done|refused|ignored","ok","message","at"}`) and an `app:` line in `log.md`; `state.sh request-wait <run> <id> [--timeout <s>]` waits for it. `app-cleanup.json` is the app's record of merged-PR cleanups. `state.sh cleanup <run>` (done / failed only) removes the run's clean worktrees, `git branch -d`, and merged PRs' remote branches. repos.json repos may carry `"liveTests": true`. Guard: the orchestrator runs no raw `git worktree …` / changing `git branch` / `git push --delete`; `requests/` and `app-cleanup.json` are guard-protected; a pipeline sub-agent never runs `claude`, and `scripts/skill-e2e/golden.sh` / `bmad_spike.sh` only as the Implementer or PR Reviewer in its worktree of a `liveTests` repo. Details: run-folder.md, "AFK runs".

## What the app reads

`status.json`, `log.md`, `gates/*.yml`, `report.md`, `memory.sh status` output, the session JSONL under `<account dir>/projects/...` (A2, P3), hook-forwarder events, and (0.5.0) `requests/*.json`, of which it uses only the kind.

## App side as built (P3a)

- `--settings`: the app reads `plugin/launch/settings.json` (when present), lays its own keys over a copy (today the usage `statusLine`; the A2 hook-forwarder `hooks` come with A2) and passes the merged JSON inline as one `--settings` value. Nothing is written into the plugin, repos or `~/.claude*`.
- `--append-system-prompt-file`: Eagle-Eye uses `<run dir>/memory-prompt.md`, role tiles `<app data>/launch/<uuid>-memory-prompt.md`; omitted when `memory.sh` is missing or fails.
- `DCV2_TAB_ID` / `DCV2_HOOK_PORT` / `DCV2_HOOK_TOKEN` (A2) are set on every dcv2 tab (as built in P3b, below).
- A tab resumed with `claude --resume` gets the same env and flags but no prompt; an Eagle-Eye tab started fresh again on a run that has a `status.json` sends `/dcv2:eagle-eye resume run=<dir>` instead of `run=`.
- The app drops an inherited `DCV2_TEST_MODE` from every dcv2 tab.
- The plugin folder: `DCTV2_PLUGIN_DIR`, else (debug builds) the repo's `plugin/`, else the bundled resource `<resources>/plugin`.
- Background starts: after a dispatcher start (queue, wave, eval, Start now) the app emits `tabs-changed` with `emit_to` to the new tab's window label only (payload: the tab id). It never focuses, unminimizes or raises a window, and it does not change the window's active tab when the window already has one (a window with none gets the new tab). The window reloads its tabs. `get_app_state` also reports `pendingStart` on a launch tab created while the app runs whose terminal has not spawned yet (it is empty after a restart, so restored tabs never count). The window opens every pending tab's terminal in the background after each load of its tab list, so a start does not depend on the event arriving. The user's own start and resume are unchanged: the new tab becomes active.

## Observability as built (P3b)

- **Hook forwarder.** `dcv2-hook` is a second `[[bin]]` of the app crate (`src-tauri/src/bin/dcv2-hook.rs`, std + serde_json only). The app adds `hooks` to the merged `--settings` (appended after the plugin's own hook lists), each running `'<dcv2-hook>'` with a 5 s timeout. The forwarder reads stdin (≤ 1 MiB), POSTs a reduced payload to `127.0.0.1:$DCV2_HOOK_PORT/hook` with `X-Dcv2-Token` / `X-Dcv2-Tab` (300 ms per step), prints nothing and exits 0. It never sends the prompt, tool input/output or last message. A payload cut at the 1 MiB cap still sends the ids read from its start. The two lists below are checked against `observe/hooks.rs` `EVENTS` and `observe/forward.rs` `KEPT_FIELDS` by a test.
  - The app registers hooks for: `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `SubagentStart`, `SubagentStop`, `Stop`, `StopFailure`, `Notification`, `PermissionRequest`, `SessionEnd`, `PreCompact`, `PostCompact`, `PostToolBatch`, `PostModelSwitch`
  - The forwarder keeps only: `hook_event_name`, `session_id`, `agent_id`, `agent_type`, `notification_type`, `tool_name`, `tool_use_id`, `source`, `reason`, `trigger`, `to_model`, and the derived `batch_tool_ids` (up to 64 tool use ids of a PostToolBatch, 200 chars each; a payload cut at the 1 MiB cap forwards none), and a count of running `background_tasks` (`background_running`)
  - Recorded on Claude Code 2.1.287 but not registered: `PreModelSwitch` (`PostModelSwitch` carries the same ids after the switch), `FileChanged` and `CwdChanged` (path-only payloads; a file-watch event says nothing about Claude's progress and would move the watchdog's hook clock).
  - Not verified: `PermissionDenied` (it did not fire for a manual "No").
  - Never registered: `WorktreeCreate` and `WorktreeRemove` (a `WorktreeCreate` hook replaces Claude Code's own worktree creation).
  - `PreCompact` sets `working` and `compacting`; the watchdog holds off a compacting tab like a running tool (twice the threshold). `PostCompact`, `SessionStart`, `SessionEnd`, `Stop`, `StopFailure`, `UserPromptSubmit`, `PreToolUse` and the program exiting clear `compacting` (an interrupted or failed compaction sends no `PostCompact`). `PostModelSwitch` sets the tab's `model`; `SessionStart` clears it. Never forwarded: `compact_summary`, `custom_instructions`, `tool_input`, `tool_response`, `file_path`, `cwd`, `old_cwd`, `new_cwd`, `transcript_path`, `prompt_id`.
- **Where the binary is.** `DCV2_HOOK_BIN`, else `dcv2-hook` beside the app executable: `Contents/MacOS/` in the bundle (Tauri bundles every `[[bin]]` of the crate there, so no `externalBin`/sidecar triple-named copies are needed), `target/<profile>/` in dev. On Windows it is `dcv2-hook.exe` beside `dcterminalv2.exe` in the install folder: the NSIS installer carries every `[[bin]]` of the crate the same way, and `src-tauri/tauri.windows.conf.json` (merged by Tauri into every Windows-target build) has **no** `externalBin`, because a missing sidecar file would fail each of those builds, including the build of `dcv2-hook` itself. `npm run release:win` runs `scripts/verify-win-bundle.mjs` and fails with "dcv2-hook.exe is not in the NSIS bundle" if the installer script lacks it. `tauri dev` builds only the app binary; run `cargo build --manifest-path src-tauri/Cargo.toml` once to get `dcv2-hook` (without it a tab simply has no hook state).
- **Which tabs get hooks.** Every Claude tab, not only the tabs dcv2 launches for a run, while the setting `observe.hooksAllTabs` is on (default on; Settings › "Track activity in every Claude tab"). With it off, only launched run tabs get them, as before. A plain tab's hooks only feed its activity dot and usage popover; `with_hooks` merges them into the user's own `--settings`.
- **Listener.** One std-thread HTTP listener on `127.0.0.1:<random port>` per app run. Each launch of a dcv2 tab gets a fresh token (the previous one stops working); a post with another tab's token, an old token or no token gets 403. Connections: at most 32 at once (extras dropped), 2 s for a whole request, 8 KiB of request line + headers. A closed tab's token goes. States: `working` (prompt submitted, tool done, sub-agent started, or `Stop` with background sub-agents still running), `waiting` (`Stop` with none, `idle_prompt`), `needs-you` (`PermissionRequest`, other notifications).
- **Session log (A2).** The session `SessionStart` last named (after `/clear` or a resume), else the tab's saved one: its `<config>/projects/*/<session id>.jsonl` and `<session id>/subagents/agent-<id>.jsonl` (+ `.meta.json` with `agentType`) are tailed from byte offsets; a partial last line waits, a shorter file is read again from 0, usage is deduped by `message.id`. Sub-agents: `Agent`/`Task` `tool_use` → `toolUseResult` (`async_launched` or `completed`, `agentId`) → `<task-notification>` (`<tool-use-id>`, `<status>`) for background ones. Read-only.
- **Cost/time (R9).** Per stage (the `log.md` stage at the message's time, else status.json's stage) and per agent: tokens (input, output, cache writes 5m/1h, cache reads) and an **estimate** at API list prices (`observe/price.rs`, the one table). Minutes are active time, with two rules because the inputs differ in density. Transcript events (`observe/transcript.rs` `ACTIVE_GAP_MS`, 5 min): a gap longer than that is excluded. `log.md` lines (`run/record.rs` `IDLE_CAP_MS`, 30 min): a longer gap is clamped to 30 min, not dropped, because an agent can work 20 min between two orchestrator lines. AgentFlight active time uses `ACTIVE_GAP_MS`.
- **Watchdog (R2).** Setting `run.watchdogMinutes` (default 10, 0 off): no status.json change and no write to any of the session's log files for that long, while `waitingFor` is null, the run is not `done`/`failed`, the tab is not `needs-you`, no tool is running (`PreToolUse` without its `PostToolUse`) and no hook event came in that time → "No progress for N min" with **Nudge** (types `continue from status.json`, then Enter 150 ms later, only on click; refused and hidden while the tab is `needs-you`; with no hook state it asks first) and **Resume** (`resume_run`).
- **Waiting (ticket 14yq6g30vmd).** The same minutes setting: when `waitingFor` is set (counted from the status.json change) or the tab is `needs-you` (counted from the hook state's `activitySinceMs`, set only when the activity changes, so a `SubagentStop` does not restart it) for that long, the panel says "Waiting for you for N min". The verdict is `observe/watchdog.rs` `waiting()`, next to `check()`; it never shows a stall.
- **Context meter (A4).** The session's last main-chain message: input + cache writes + cache reads against the model's window (haiku and 4.x 200K, 5.x 1M, `[1m]` 1M); warns at 60%, never sends keys. The app check log is shown trimmed (ANSI and `\r` redraws stripped, head 40 + error lines + tail 80).
- **Version (R3).** `observe/version.rs`: `CLAUDE_MIN` 2.1.287, `CLAUDE_MAX_TESTED` 2.1.287. Out of range → banner. When no self-test result exists for the detected version, the banner offers a one-click self-test: `claude -p --model haiku --plugin-dir <plugin> --output-format stream-json --verbose --max-turns 4 --no-session-persistence` in a temp folder (own process group, killed whole on timeout) (`CLAUDE_CODE_SUBAGENT_MODEL=haiku`, `DCV2_STOP_HOOKS=off`, 45 s timeout) asking for one foreground `dcv2:plan-reviewer` agent; passes when the init lists the dcv2 plugin and agent, the agent completes and the result says `SELFTEST-DONE`. Stored in `<app data>/claude-selftest.json`.
- **Fixtures (A5).** `src-tauri/src/fixtures/claude-2.1.287/`: hook payloads, a session log with one sub-agent, and the self-test stream, recorded from one haiku run in a toy folder and sanitised (paths → `/work/toy`, `/config`, `/app/plugin`; attachments other than `model`/`date` dropped; signatures blanked). `Notification` and `PermissionRequest` cannot fire under `-p`; their `*.synthetic.json` copies follow the shape recorded on 2.1.299 by ADE. Contract tests parse all of them.
  - **Failing session (AF5).** `projects/-work-toy/5b0d6e0e-3a52-4c61-9d1f-7a2c4e8b9f10.jsonl` is a trimmed excerpt of a recorded 2.1.287 e2e session (the prompt, a guard-blocked Bash call, a failing Bash call, a closing message) with the identity removed (home path, temp path, account folder, injected context and the email are gone; paths → `/work/toy`, `/config`, `/app/plugin`; ids fresh). The recorded session holds no `Edit`, so its `Edit` call and result are built from the 2.1.287 `Edit` shape. `observe/transcript.rs` tests parse it and scan every file under `claude-2.1.287/` (secrets, identity strings, email shapes, absolute paths outside those three roots; the one `/tmp/scratch` of the self-test stream is allowed by name).
  - **How a guard block appears in a 2.1.287 transcript.** A `type: "user"` line whose `message.content[0]` is a `tool_result` with `is_error: true` and content `PreToolUse:Bash hook error: [bash "<guard.sh>"]: Blocked by the dcv2 guard: <reason>` followed by `This hook comes from the dcv2@inline plugin.`; the same line carries a top-level `toolDenialKind: "permission-rule"` and `toolUseResult: "Error: PreToolUse:Bash hook error: …"`. A plain failing command is `is_error: true` with content `Exit code N\n…` and no `toolDenialKind`. A failed API turn (`StopFailure` writes nothing itself) is an `assistant` line with top-level `isApiErrorMessage: true`, an `error` kind string, an optional `apiErrorStatus`, and `message.model` `<synthetic>`.

## Session Inspector (AgentFlight M1)

The Trace panel (run panel › Open trace, a FleetTimeline lane, or the palette) shows what the agents of a run did, from Claude Code's own transcripts, read-only.

- **Where it lives.** `src-tauri/src/flight/` is a pure core (std, serde, regex, sha2, plus base64 and chrono): `adapters/claude.rs` turns the main and `subagents/agent-*.jsonl` logs into schema-1 events (`flight/schema.rs`, mirrored in `src/flight/types.ts`), `correlate.rs` and `derive.rs` build spans, the agent tree, failures, files touched and repeats, and `redact.rs` is the one secret scanner (also `clickup::secret_scan`, the same verdicts as `memory.sh`). Only `flight/host.rs` may name `crate::` (a source scan in `flight/mod.rs` enforces it, skipping test items). The tailer moved to `flight/tail.rs` and is re-exported as `observe::tail`.
- **Events hold no content.** An event carries names, ids, paths, exit codes, error kinds and counts, plus a ref (file, byte offset, length, sha256) to the transcript line. The text is read only by `flight_content`, which checks the sha256 ("source changed" on a mismatch), accepts only files of the run's or session's resolved set, and always redacts: each unescaped string value of a tool input is scanned line by line, and a hit line becomes `[redacted: <kind>]`. The count is returned.
- **Capture policy.** Settings › Activity › Session Inspector sets `off | metadata | redacted | full` per account (old files load as `metadata`). The policy comes from the account that owns each session's `config_dir` (`resolved_account_config` + `same_config_dir`), never from the window: the strictest across a run's sessions wins, a folder that matches no configured account is refused (`unknown account folder`), a run `meta.json` `flight.capturePolicy` may only tighten it, and `off` opens no file. Every policy but `off` shows content on click, redacted; nothing is stored.
- **Commands.** `flight_session({runDir | configDir + sessionId, agent?, cursor?, pageSize?})` (default 200, max 1000) parses on a worker thread through `FlightCache` (its own managed state, keyed by each file's real path, size and mtime, the 8 newest sessions) and returns the agent trees, failures (repeats nested, the 5 events before each) and one page. The cursor is the last returned (time, file, offset, index) key as opaque base64 JSON, so lines appended between pages never repeat or skip an event. A line flushed later with an earlier timestamp than the cursor shows up only after Refresh (the panel says so). Nothing in `run/` or `observe/attention.rs` calls it (source-scanned), so `list_runs` and the sweeps never read a transcript.
- **Timing.** The gate times the first page of a generated 2 MB session (under 1 s, debug build). The 20 MB check (SM-2) is `#[ignore]`d because a debug build is too slow for it: run `cargo test --release flight_first_page_20mb -- --ignored` in `src-tauri/`.
- **Derived labels.** A failure is `exact:is_error`, `exact:hook-denial[:dcv2-guard]` or `exact:stop-failure`; a repeat is `heuristic:same-tool-same-input-after-error`; a sub-agent's PR id is `heuristic:description-prefix` (from a description starting `PR<n> `). The panel shows a "derived" pill for every heuristic.

**Run records, run-level Trace and the trace index (plugin 0.7.0).**

- **Run lane.** `flight/adapters/dcv2_run.rs` (pure) turns a run folder into Events on an `orchestration` lane (`agent.id`, provider `dcv2`): stage changes, approval waits and decisions (the bands come from `run/timeline.rs` `approval_bands` through the host), checks of three sources (`skill` from status.json, `app` from app-checks.json, `stop-check` from log.md), review rounds, CI, `pr` lines, retries, requests and `logs/guard.log`. Each points at its log line or whole file (offset, length, sha256) and holds no log text. A malformed or over 8 MiB file is a notice. The files it may read are listed by the host (`run_file_list`); `flight_content` opens only those, always redacted, cut at 256 KiB.
- **One order, one failure, one phase.** `session::merge` pages transcripts and run Events in one (time, file, offset) order. A `guard.log` line merges into the transcript's guard block by `tool_use_id` (one Failure, with `rule`), a failed check is a Failure (`exact:check-fail`), and `derive::phases` gives each Event its stage and PR state (`exact:log-line` from the `pr` lines, `heuristic:status-now` for a run before them). A sub-agent's PR is `exact:pr-description` when the run's `meta.json` `pluginVersion` is at least 0.7.0 (`EXACT_PR_FROM`, tied to `plugin/VERSION` by a test).
- **Policy of a run.** A run's folders are its recorded sessions' plus `meta.json` `account.configDir`; a run with neither is refused (`no account for this run`), an `off` account opens no run file either.
- **Trace index.** `<app data>/flight.db` (rusqlite, `bundled`, WAL) holds Events, Spans and source refs, no content. One thread (`flight-index`, spawned from `lib.rs` through `flight::host::spawn_index`, never from `run/` or the sweeps) waits 30 s and then runs a pass every 30 s. A run whose watermarks (size, mtime, head hash) are unchanged is skipped; a changed session is parsed whole, because the transcript adapter needs whole files, so a two-pass index equals a one-pass one. At most 16 runs and 64 MiB per pass. It is a cache: deleting it loses nothing.
- **Search.** `flight_search({kind?, nameContains?, status?, stage?, prState?, prRole?, inReview?, repo?, from?, to?, text?})` takes values only (no SQL text), runs on a worker thread outside the store locks, on a read-only connection, and returns runs newest first with a match count and the first matching Event id, the runs excluded because their account is `off`, and the index progress. `flight_session` takes `focus` (an Event id) to start the first page at it. The UI is "Search traces" (palette, and the Trace header).
- **Rollback.** Revert the PR and delete `flight.db`. A 0.7.0 run still going keeps correct records, but the old `timeline.rs` does not filter the new log lines, so that run's wait minutes come out short.

## Compare, keep and evaluate runs (AgentFlight Wave 2, plugin 0.8.0)

- **Settings.** `claudeAccounts[].keepRunTraces` (per account, default off; Settings › Activity, disabled when the capture policy is `off`) and `observe.evalEnabled` (app-wide, default off; "Eval mode"). Old settings files load with both off.
- **Snapshots.** After each index pass the `flight-index` thread runs `snapshot_pass` over the same run folders: a run whose app-usage.json outcome is `done`/`failed`/`eval-done`, whose account keeps run traces and whose policy is not `off` gets `<run>/flight/` (format in run-folder.md), at most 2 per pass, once per terminal record. Under `metadata` it holds Events and source refs only; content is kept only under `redacted`/`full` and served only while the current policy is `redacted`/`full`. A session whose transcript is gone is read from the snapshot (the Trace shows a Snapshot pill); a live transcript always wins. Nothing in `run/` or `observe/attention.rs` names `flight::`.
- **Compare.** `flight_compare({a, b})` (worker thread, read-only `flight.db`, never indexes on demand) returns rows in the fixed order stages, tools, failures, retries, repeats, files, checks, tokens, windowShare, the first differing row being the Divergence. The same run twice is refused. UI: Compare page from Trace search (two selected runs) or the palette ("Compare runs").
- **Eval groups.** `dispatch_eval_start(window_id, source_run_dir, n)` (Eval mode on, n 2..10, a finished non-eval source with no `mode`, the window's account equal to the source's) queues n entries on the dispatch queue (review mode `local`, `force`, `eval` with `bases`). An eval entry holds when a usage hold is set and the account has no five-hour reading at all ("the five-hour usage is not known"); a reading past its reset is clear. "Start now" never skips the hold for an eval entry, and `pick` passes over a held eval entry, so it does not block normal, wave or other-account entries. A finished eval run is not a duplicate of a normal start.
- **Attention.** `eval-finished` (eval group finished; in Settings and the phone push list; fires once, never `batch-ready`) and `run-done` with detail `eval` (an eval run reached `ship-approval`; no approval-wait or waiting-reminder). Finished eval runs are left out of active runs.
- **Eval app check.** The dispatch tick runs R1 once per finished eval run without app-checks.json (one at a time, own thread, local commands only, no usage). `flight_eval_results(group)` returns per-run measures and min/median/max over finished runs; a check pass rate with no app-checks.json is null ("not checked").
- **Eval cleanup.** `clean_up` (typed `cleanup` request, "Clean up worktrees", the eval results Clean up) accepts a finished eval run; `run/cleanup.rs` stays `done`-only. Branches stay (`git branch -d`); `eval_delete_branch` is the app's only `git branch -D`, for a finished eval run's own expected branch with no worktree, after a user confirmation.
- **Rollback.** An older build shows a finished eval run as waiting at ship approval and has no state.sh refusals: do not resume an eval run there. Snapshots and meta.json `eval` are ignored by old builds.

## Export, replay and re-run (AgentFlight Wave 3)

- **Export (AF12).** Trace header "Export" opens a dialog that builds a Preview first (`flight_export_preview`: policy, encoding, endpoint, span/event counts, size, every attribute key that leaves with how many spans or events carry it, sha256 digest, loopback flag). `flight/export.rs` (pure, no IO) builds one OTLP `ExportTraceServiceRequest` per Trace with the GenAI semantic conventions (`SEMCONV` 1.37.0), as OTLP/HTTP protobuf (default, `application/x-protobuf`, hand-encoded, field numbers in one table) or JSON (`application/json`, hex ids, integer enums, 64-bit integers as strings). Agents are `invoke_agent` spans, tool calls `execute_tool`, `llm.call` a zero-length `chat <model>` span; orchestration Events are span events on one `agentflight.run` span. Span ids hash the agent and `tool_use` or message id (Event ids hash the transcript path and would differ per machine). Golden payloads: `src-tauri/src/fixtures/flight/otlp-wave1.json` and `.pb.hex`.
- **Policy clamp.** `off` cannot be exported. Tool arguments and results leave only under `full`, and `full` is used only when the account's capture policy is `full` and the request carries `confirmFull` (an unticked checkbox every export); otherwise the Preview says it fell back to `metadata`. Tool text is read through the same checks as `flight_content`, redacted, and cut at 16 KiB each. A payload over 32 MiB is refused.
- **The previewed bytes.** The host keeps the bytes of the last Preview (one entry, replaced by the next Preview). `flight_export_send` and `flight_export_save` take the digest and act on exactly those bytes, so a Trace that grew after the Preview is not re-read; an unknown digest is refused with "the trace changed since the preview".
- **Network path.** Send is one POST on its own `ureq` agent (`flight/host.rs` `export_agent`): http or https with a host, `max_redirects(0)`, no proxy (`HTTP_PROXY` and friends are not read, so a loopback export stays on loopback), 30 s, no retry; a non-2xx reply is an error with its status line. A non-loopback endpoint shows "This export leaves the machine: N spans to <endpoint>" before Send. Save writes to the picked absolute path (created or truncated, never through a link).
- **Endpoint setting.** `observe.exportEndpoint` (Settings › Activity › "Export endpoint"), default `http://127.0.0.1:6006/v1/traces` (Phoenix). Only `http://` and `https://` addresses with a host are saved; an invalid value is refused with the reason and the old one stays. The dialog starts from it and can change it for one export (Enter rebuilds the Preview, never sends).
- **Event replay (AF13).** Read-only. `flight_replay_track(target)` returns one tick per Event of the Trace in `flight_session` order (at most 20,000, then `truncated`): `{id, at, kind, name, status, file, checkSource, pr}`, where `file` is the number of files a `file.change` touched and never a path. `flight_replay_file(target, eventId)` rebuilds the file a `file.change` changed as it was after that edit: the PR's `baseCommit` (from status.json) plus the recorded successful edits of that file up to it, read from the transcript lines in memory (`flight/replay.rs` is pure: Write, Edit, MultiEdit; an old text that is absent, or found twice without `replace_all`, stops the file at the state before it and says why). Text is redacted, cut at 256 KiB and never written. It says why it cannot show a file: policy `off`, a notebook, a file outside every PR worktree, a file over 2 MiB, a base commit that is not in the repo, a gone transcript.
- **What replay cannot see.** Changes made by shell commands (`sed -i`, a formatter, `git checkout`) are not edit tools, so the rebuilt file does not include them. Nothing recorded is ever run: no replay path passes a recorded tool input to a shell or a tool (a source scan and a fixture whose recorded Bash call is `rm -rf <sentinel>` pin it).
- **After the run's worktrees are cleaned up.** Replay never verifies, reads or opens a PR's worktree folder (`run/cleanup.rs` removes it for a merged run). The file path is matched against `janitor::expected_worktree` of the verified repo (`janitor::verified_repo`) as text, and the base comes from `git show <baseCommit>:<path>` in that repo (`run/git.rs` `git_bytes`), so a merged run still replays.
- **Check re-run (AF13).** On an app `check.end` row in Replay mode, "Re-run check" (two clicks: the button, then "Re-run" in a confirmation that shows the command, the setup, the check folder when it is not the root, and the commit) runs the PR's recorded app check again at the commit it ran on (`app-checks.json` `head`, which must still be a commit in the verified repo). The command is the app-written one in `app-checks.json` and the setup is the repos.json `setup` string, else (only for a run whose meta.json has `reviewMode`) the lockfile table `npm ci` / `pnpm install --frozen-lockfile` / `yarn install --frozen-lockfile` / `go mod download`, exactly the rule of `plugin/scripts/state.sh` `detect_setup` (a parity test reads it). `run/rerun.rs` owns it; nothing a transcript recorded is ever run.
- **Scratch worktree.** The re-run happens in a detached worktree the app makes with `git worktree add --detach` at `<repo parent>/<repo>-worktrees/dcv2-replay-<runId>-<pr>-<n>` and removes with `git worktree remove --force` (the only forced removal in the app): `janitor::remove_scratch` acts only when the name matches that pattern, the parent is that repo's own `-worktrees` folder and git lists the path as `detached` (a `locked` entry is unlocked first; no branch is ever touched, contract worktrees never match).
- **Working folder.** Setup runs at the scratch worktree root (as `state.sh` does for a new worktree: 10 min limit). The check runs in the recorded check folder: `AppCheck.cwd` made relative to the PR's worktree path (`janitor::expected_worktree`, used as text only) and joined onto the scratch path through `check_folder`; a folder outside it is refused and a folder that does not exist at that commit is an `error`. The contract worktree is never the working folder and need not exist, so a merged run (worktrees cleaned up by `run/cleanup.rs`) still re-runs.
- **One at a time.** One re-run runs in the whole app (a second request gets "a re-run is already running"); a drop guard frees the slot even if the thread panics. Stop (`flight_replay_check_stop`) kills the process tree through `run::check::run_one_stoppable` and the result is `stopped`; `check::kill_all` at app exit covers it too. Closing the Trace does not stop a re-run.
- **Records.** `<app data>/flight/replays/<runId>/<PR>-<n>.json` plus `<PR>-<n>.log` (first line `$ <setup>`, then its output, then `$ <command>` and its output), written atomically before the worktree is made and after every state change (`preparing`, `setup`, `running`, then `pass`, `fail`, `timeout`, `error`, `stopped` or `interrupted`). Fields: `runId, pr, n, repo, worktree, commit, command, setup, cwd` (relative, `""` for the root), `recorded` (the recorded check's result), `state, exitCode, startedAt, finishedAt, detail, log` and `scratchLeft` when removing the worktree failed. The newest 5 per run and PR are kept. Nothing is written in the run folder.
- **Cleanup at start.** Before the index thread's first sleep, a record still `preparing`, `setup` or `running` that no live re-run holds becomes `interrupted` and its scratch worktree is removed; a `scratchLeft` record is retried; the records of a run folder that no longer exists are deleted.
- **Commands.** `flight_replay_check_info({runDir, pr})` (the confirmation's content, or the reason there is none), `flight_replay_check`, `flight_replay_check_stop`, `flight_replay_checks(runDir)`, `flight_replay_check_log({runDir, pr, n})` (the log's tail). Policy `off` refuses them.
- **Not built.** The local telemetry receiver (CAP-17) is deferred until a gap that transcripts do not cover is written down here.

## Attention (tabs that need you)

One backend thread, `observe/attention.rs`, started at app setup (never from a command, so it works with no window open on a panel), decides every notification, in-app notice, badge and reminder.

- **Fast pass, every 2 s**: the open tabs of all windows, their hook state and trackers (the same `observe_tab_now` the run panel uses, so one verdict), and for each run tab the run folder's `status.json`, `app-checks.json`, `app-cleanup.json` and the signed auto-post record.
- **Background pass, every 60 s**: the app's own runs (not adopted) changed within 30 days that have no open run tab: `status.json`, `app-cleanup.json` and the auto-post record only. The cleanup sweep acts on runs hours after their tab was closed, so merged-cleaned (and a late auto-post result) must be seen without a tab.
- **The auto-post record** is read (`clickup::trust::read_autopost`) only when drafts are written and ship is approved (`autopost::may_be_due`), the record file exists and its mtime changed since the last read; the keychain key is read once and cached. A read error is logged once per run and counts as "no change".
- **Events** (edge-triggered, keyed by subject and kind): needs-you, approval-wait, stall, not-started (a launch tab created while the app runs whose terminal has not started within 60 s of the tab's `createdAt`, one event with the tab as subject; the text is "dcv2: <tab> was created but not started (<run id>)", without the parenthesis when the tab has no run folder; tabs restored at app start never count, because their terminals open lazily on first show), run-done, run-failed, check-failed, ci-failed (a PR's GitHub CI in `app-github.json` that becomes `fail`, per PR, debounced like check-failed), autopost-failed (a result that becomes `failed`, per ticket), waiting-reminder (one per episode, after `run.watchdogMinutes`) and merged-cleaned (an `app-cleanup.json` record that becomes final with outcome `cleaned` or `kept`). The first tick after start is silent, a run that first enters a pass is seeded silently, and the same subject and kind is not announced twice within 30 s.
- **Push events** (`PushDiff` in `attention.rs`, constants in `notify.rs`). Beside the attention diff the same thread emits app-wide `tab-state` (a tab's activity, tool running or sub-agents changed), `run-state` (a run's stage, approval stop, PR progress or checks changed; a run that first appears after the first tick) and `stall` (a tab's stall flag flipped) events, only on a change; the first tick is silent and a payload is ids and state fields only. A run missing from a fast tick (a run with no open tab is read only on the 60 s background pass) keeps its memory and emits nothing; it is forgotten only on a background tick that does not list it, exactly like the attention diff. The page (`src/run/events.ts` `usePushRefresh`) refreshes on mount, on an event and on window focus, and polls at 15 s or more while events arrive and at the view's old interval (2 to 4 s) when none arrived for three periods or the subscription failed, so a view never freezes.
- **Landing.** Desktop notification actions are ignored, so an event notified while no window of the app has focus leaves a target (tab, time). The next app activation within 120 s (a window gaining focus after no window had it for at least 250 ms, or a dock click) selects that tab (`run::focus_tab`). A switch between the app's own windows is faster than 250 ms and never lands. Choosing a tab clears the target.

- **Sinks** (`observe/notify.rs`, `route()`): the in-app notice (an app-wide `attention` event; every window shows it with Go to tab and Dismiss, at most 3, 15 s) is always sent, because macOS shows no banner and ignores the bounce while DCTerminalv2 is the frontmost app; the system notification (tauri-plugin-notification) is always sent; the dock bounce only while no window has focus (critical for needs-you and approval-wait). The dock badge (macOS) is the count of tabs that need you (needs-you, or the run waits at an approval stop), set app-wide on one window and cleared at 0. Settings › Notifications has a master switch (notices, system notifications, badge and bounce) and one switch per kind (`notify` in settings.json, default all on). The plugin reports `granted` on desktop whatever macOS decides, so Settings also shows the "macOS blocks notifications" hint when the test notification is refused. Run events are also logged to the run's `log.md` (`app: attention …`).

- **Batch and wave milestones** (`run/dispatch.rs`): three more event kinds, `batch-planned` (every counted run of a batch has its plan ready for approval), `batch-ready` (every one is ready to ship) and `wave-ready` (an epic's next wave can start). Each fires once (remembered in `dispatch.json`), carries the batch id or epic run id as its subject, and goes through the notifier like any event: one desktop notification (in-app notice or system, per the notification settings), and a phone push when the push target is not `none` and `run.batchPushes` (default on) allows it; the push payload is only `{run, event}`. Nothing is suppressed: there are no per-run approval pushes, and a batch member's desktop approval-wait notification fires exactly as for any other run, whatever the push target and `batchPushes`. The Active runs popover and the Runs view show a batch overview (one row per run: stage, what it waits for, PR link, CI from `app-github.json`, a waiting-for-you count, a filter by batch, a removed run struck through).
- **Phone push** (`observe/push.rs`, Settings › Phone push). Target `ntfy` (POST `<server>/<topic>`), `pushover` (POST api.pushover.net) or `webhook` (POST JSON). A push carries exactly `run` and `event` (the run id and the kind: stall, not-started, check-failed, ci-failed, merged-cleaned, autopost-failed; each has its own switch) and nothing else. The ntfy topic, Pushover token and user key and the webhook URL are in the keychain (service `com.jtfrancisco.dcterminalv2.push`); settings.json holds only the target, the ntfy server and the switches. Addresses must be https (http only for this machine). Sending is on a worker thread of its own with a bounded queue, 10 s per call and one retry, so a slow push never delays the detector; failures are logged. "Send test" reports the result inline.

- **PR card actions** (`run/actions.rs`). Copy branch (the page), and Reveal, Open in editor and Shell here on a PR's worktree. The backend resolves the worktree from the run and PR id and acts only when `janitor::verify_worktree` accepts it (where the contract puts it, a linked worktree of the PR's repo, on the run's branch); otherwise the buttons are disabled with the reason. The editor is `ui.editorCommand` (empty: `code`), split into program and arguments and started without a shell with the worktree last. Shell here opens a Shell tab in the calling window.

- **Run panel layout** (`RunPanelShell.tsx`). The panel beside a run tab is 16 to 40 rem wide (default 20): drag the 6px handle, or focus it and press Left (wider) or Right (narrower) for 1 rem; double-click resets. The button at its top edge collapses it to a narrow rail with the stage dot, which turns to the attention colour while the run waits for you; clicking the rail expands it. Width and state are kept per window in localStorage (`dcv2.runPanel.<windowId>`); the terminal beside it refits after each change.

- **Duplicate start** (`run/duplicate.rs`). `start_run` (Eagle-Eye) takes `force`. Without it, an unfinished run (not `done`, not `failed`; no status.json yet counts as unfinished) with the same request words (whitespace-normalised, the ticket lines left out), the same folder (canonical) and the same set of ClickUp ticket ids makes it answer a typed `duplicate {runId, runDir}` and start nothing. The start screen then offers Resume that run (`resume_run`, which focuses a live tab of it) or Start anyway (`force`).

- **Active runs** (status bar). `attention_summary()` returns `{needsYou, activeRuns}` from the detector's latest reading: the tabs that need you in every window (needs-you, or a run at an approval stop; it does not follow the notification switches, since it is information, not a notification) and the unfinished run tabs. The status bar shows it right of the account ("2 need you · 3 runs", hidden at 0), refreshed every few seconds, on window focus and on the `attention` event. Clicking it opens Active runs (`active_runs()`: window, tab, stage, waiting / no progress, PRs done of total; read at most every 3 s while open) with Go to tab (`focus_tab`, which may switch windows), an Open dashboard button and a link to the Runs view. `run_tabs()` is the same reading with the done and failed run tabs kept (the tab progress and the run dashboard use it); each tab also carries `waitingSince` (status.json `updatedAt` while it waits, approximate) and `prs` (id, state, app check, CI, PR state).

- **Run dashboard and analytics** (`RunDashboard.tsx`, `RunAnalytics.tsx`; Cmd+K › "Run dashboard" / "Run analytics", the Active runs popover's Open dashboard, the Runs view's Analytics button). Window-level pages drawn as a layer inside the workspace body, so the terminals underneath stay mounted; Escape, Close or selecting a tab closes them. The dashboard lists one card per unfinished run tab of every window (steps, a pill per PR, how long it has waited, Go to tab) from the same `run_tabs()` read that draws the tab bar's progress underline (PRs done of total, an outline while the run waits for you, danger for a failed run); it refreshes on `run-state`/`tab-state` and its minute clock calls no command. Analytics reads `run_overview` once and draws three inline SVG charts (estimated cost, duration, waiting share per finished run) with folder and repo filters; every cost is an estimate at API list prices. The Runs view is a table: Duration and Estimate sort (runs without the figure stay last) and its header totals the runs of the last 7 days.

- **Recently closed** (macOS File menu, and the start screen of an empty window). File › Recently Closed lists the focused window's closed tabs (label, folder, time, at most 10; item ids `reopen-closed:<tab id>`) and reopens the chosen one, not only the newest. The macOS menu is app-wide, so it is rebuilt when a tab closes or reopens and when another window gains focus.

- **A tab whose folder is gone** shows "Choose another folder…" (`set_tab_folder`): the tab keeps its id and its name (a name that follows the folder follows the new one) and starts in the new folder. Its saved Claude session is kept only when that session's log is under the new folder's Claude project folder (`<config>/projects/<path with every non-alphanumeric as ->`/`<session>.jsonl`), otherwise the tab starts a new conversation.

- **Split panes.** A tab has at most two panes. Split right / down (the tab's context menu, Cmd+D and Cmd+Shift+D; Ctrl+Shift+D and Ctrl+Shift+Alt+D elsewhere) adds a Shell pane in the tab's folder (`TabRecord.split`: direction, the first pane's share 0.2 to 0.8, the second pane's id, kind and folder; a state.json without it loads as before). The terminal id is the tab id for the first pane and `<tab id>:p2` for the second; the PTY registry, `live.ts` and `park.ts` key by terminal id, and closing a tab stops both terminals (`kill_tab_pty`), forgets both (`ObserveState::forget`), and counts both as live work on quit. The second pane is a Shell, so it has no hooks, tracker or usage line of its own and can never replace the first pane's. Cmd+Option+Arrow (Ctrl+Shift+Alt+Arrow elsewhere) moves between the panes; Cmd+W closes the focused pane when the tab has two (the tab when it has one). Closing the second pane leaves the tab as it was; closing the first pane stops both terminals and the second pane's shell restarts as the tab in its folder; a run's first pane is the run, so closing it closes the tab. The tab's dot shows its most urgent pane.

## Import from the dev app (release builds)

Debug builds keep their data in `<identifier>.dev`, release builds in `<identifier>`. On first launch (offered once; `dev-import.json` records it) and from File › "Import from dev app…" (hidden in debug builds) the built app imports the dev app's session, reading `.dev` only:

- **Windows and tabs**: each dev window (open or closed) comes in as a closed window on its account (dev accounts matched to this app's by config folder, else added; a window whose account could not be added is skipped), reopened by you from File › Reopen Closed Window; its open tabs and the recently closed ones keep `claudeSessionId`, `cwd` and `claudeConfigDir`, so reopening a tab runs `claude --resume <id>` in the same folder and account. Tabs whose session is already here are skipped (a second import adds only new ones).
- **Launch re-pointed**: `--plugin-dir` → this app's plugin, `--settings` → this plugin's `launch/settings.json`, `--append-system-prompt-file` → a new file from `memory.sh compose` in `<app data>/launch/`, `DCV2_MEMORY_DIR` → this app's memory. `DCV2_RUN_DIR`, `DCV2_MAX_IMPLEMENTERS`, `DCV2_STOP_HOOKS` and the prompt are kept.
- **Runs** are adopted in place (`adopted-runs.json`, see run-folder.md); **memory** is copied when this app has none.
- **Refused while the dev app is live**: its `app.lock` is held (every build now flocks `<app data>/app.lock` for its whole life, pid inside), a `claude` process runs one of its tabs' sessions (`ps`), or a session log was written in the last 2 min → "Quit the dev app first".
- Resuming an adopted run's tab is refused while another `claude` process runs that session.
- Keychain items (ClickUp tokens, the trust key) have the same service names in both builds; macOS asks once to let the built app use them.

Guard no-write zones (run-safety hardening): in a bound run (`DCV2_RUN_DIR` set) nobody, the orchestrator included, writes with Edit/Write or a shell redirect/copy/move into the plugin folder, `CLAUDE_CONFIG_DIR` or `~/.claude*`, or the app's data folder outside the run folder (run-folder.md, Run-safety hardening). A session with no `DCV2_RUN_DIR` is not affected.

Hooks (run-safety hardening): `hooks/hooks.json` runs the guard on `Edit|Write|NotebookEdit|MultiEdit|Bash|Monitor|PowerShell|mcp__.*`. PowerShell is refused in a bound run; unbound, it gets the Bash analysis, whose known limit is that PowerShell-native writes (`Set-Content`, `Out-File`, `Remove-Item`, `Copy-Item`) are not seen. See run-folder.md, Run-safety hardening, for the MCP verb rule.

Env assignments (run-safety hardening): `DCV2_MEMORY_DIR` is set at every dcv2 launch, so the guard's rule against assigning `DCV2_*`, `CLAUDE_PLUGIN_ROOT` and `CLAUDE_CONFIG_DIR` applies in every dcv2 tab, not only in Eagle-Eye runs: hand development such as `DCV2_RUN_DIR=… bash plugin/scripts/state.sh …`, `CLAUDE_CONFIG_DIR=… claude …` or `DCV2_TEST_MODE=…` typed through Claude in a dcv2 tab is refused. `env -u NAME …` and `unset NAME` still work, `DCV2_E2E_*` and a `DCV2_RUN_DIR` / `DCV2_MEMORY_DIR` equal to the session's own are allowed, and a plain terminal is unaffected. `memory.sh --root` is refused while `DCV2_MEMORY_DIR` is set.

Guard without python3: with `DCV2_RUN_DIR` set the guard blocks every call when python3 is missing or broken (it cannot judge them); in a tab with only `DCV2_MEMORY_DIR` it blocks calls that name the memory or plugin folder (run-folder.md, Run-safety hardening).
